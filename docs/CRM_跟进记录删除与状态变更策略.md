# CRM 跟进记录：删除与状态变更策略

本文档说明「删除跟进记录」与「状态变更记录」的业务规则、四种备选方案，以及最终采用的策略与实现要点。

---

## 一、背景与问题

### 1.1 业务链条

- **线索** → 状态变为「有意向」时，可自动生成**商机**，并写入一条**状态变更跟进**（如「未跟进→有意向」）。
- **商机** → 状态变为「待签约」或「已赢单」时，可自动生成**客户**，并写入一条**状态变更跟进**（如「商机→客户」）。

因此存在「状态变更类跟进」与「普通跟进」两类记录。

### 1.2 核心问题

若允许用户**删除**某条状态变更跟进，会带来两个问题：

1. **业务数据一致性**  
   删除「线索→商机」那条跟进时，是否要同时撤回业务（删商机、线索回未跟进）？若已走到客户，再删这条老记录，是否还要撤掉商机/客户？若处理不当，会出现「删一条历史记录却导致整条链被撤掉」的混乱。
2. **链条与可追溯性**  
   若允许随意删除状态变更记录，时间线会出现断点，日后回溯或做数据分析时无法还原「谁在何时做了什么流转」。

因此需要明确：**谁可以删、什么能删、删了之后业务数据与图片怎么处理**，并形成稳定策略。

---

## 二、四种备选方案

下面四种方案的核心差异在于：**何时允许「删除 + 联动撤回业务」**，以及**是否允许删除历史状态变更记录**。

### 方案 A：只允许撤销「时间上最近的一条」状态变更

- **规则**  
  整条时间线里，**只有最新一条**带流转类型（`transitionType`）的跟进允许「删除且联动撤回」；其余状态变更跟进只能「只删记录、不撤回」。
- **示例**  
  时间线顺序：F1（线索→商机）→ F2（商机→客户）。  
  - 删 F1：只删 F1 记录，不撤回（因为时间上最近的是 F2）。  
  - 删 F2：撤回（删客户、商机回需求确认），并删 F2。
- **优点**  
  实现简单（按创建时间取「最近一条」即可），不会误伤整条链。  
- **缺点**  
  想先撤商机→客户、再撤线索→商机，需要分两次操作；规则偏「时间」而非「业务当前状态」。

---

### 方案 B：按「当前业务状态」只允许撤销「链顶」一步（推荐思路）

- **规则**  
  - **线索→商机**：只有在该线索**已转商机、但商机尚未转客户**时，删这条跟进才做撤回（删商机、线索回未跟进）；若商机下已有客户，删这条只删记录，**不撤回**。  
  - **商机→客户**：只有在该商机**已转客户**时，删这条跟进才做撤回（删客户、商机回需求确认）。
- **示例**  
  已到客户阶段时，删「未跟进→有意向」那条 → 只删记录，不动商机/客户，逻辑不乱。  
  只有「当前链顶」那一步的跟进被删时，才触发业务撤回。
- **优点**  
  与业务直觉一致（只能撤销当前这一步），不会因删一条老记录而撤掉后面的商机/客户；数据安全、可解释性强。  
- **缺点**  
  删除前需查询当前是否已有客户/商机（多一次 DB 查询）。

---

### 方案 C：两条都可删，但「撤回」仅对「链顶」执行

- **规则**  
  任意状态变更跟进都可以删（记录一定删）；**是否执行业务撤回**仅当该条对应「当前链顶」时才执行，否则只删记录。
- **示例**  
  与方案 B 在「何时撤回」上一致，只是表述从「是否允许删」改为「是否带撤回」。
- **优点**  
  与 B 行为一致，强调「只对链顶做撤回」。  
- **缺点**  
  与 B 本质相同，实现也相同。

---

### 方案 D：禁止删除「非最近」的状态变更记录

- **规则**  
  只有「时间上最近的一条」状态变更跟进允许被删除（且带撤回）；更早的状态变更跟进**不允许删除**（或仅允许删记录、不允许带撤回，视实现而定）。
- **优点**  
  绝对不会出现「删老记录导致整条链乱掉」。  
- **缺点**  
  误操作或需要修正的历史记录无法通过删除清理，灵活性差。

---

## 三、方案对比示例（同一业务链）

假设：**T1** 线索 A 从「未跟进」→「有意向」，产生商机 B、跟进 **F1**；**T2** 商机 B→客户 C，产生跟进 **F2**。当前状态：线索 A → 商机 B → 客户 C。

| 场景 | 方案 A | 方案 B / C | 方案 D |
|------|--------|------------|--------|
| 已到客户后，删 F1（线索→商机） | 只删记录，不撤回 | 只删记录，不撤回 | 不允许删 F1 |
| 已到客户后，删 F2（商机→客户） | 撤回（删客户、商机回需求确认） | 撤回 | 撤回（且只有 F2 可删） |
| 先删 F2 再删 F1（链已回退到只有商机） | 删 F1 时撤回（删商机、线索回未跟进） | 同上 | 同上 |
| 只有商机、无客户时删 F1 | 撤回 | 撤回 | 撤回 |

## 四、最终采用的策略（综合业务与可追溯性）

在考虑**数据安全、可追溯性、培训成本**后，最终采用的策略是：

- **状态变更记录：不可删除，可编辑**
- **普通跟进：可删除；删除时一并删除该跟进下的所有图片**

这样既避免「删历史导致链条断裂、分析无从下手」，又保留「通过编辑修正描述、补充信息」的能力；普通跟进仍可删，且不会留下孤儿图片。

### 4.1 状态变更记录（带 `transitionType`）

- **不可删除**  
  后端：若该条跟进存在 `transitionType`（如 `lead_to_opportunity`、`opportunity_to_customer`），`deleteFollowUpAction` 直接返回错误，提示使用「编辑」修正。  
  前端：三点菜单中**不展示「删除」**，仅展示「补充图片」「编辑」。
- **可编辑**  
  创建者或管理员可编辑该条的：跟进内容、沟通对象、一句话进展、下一步、客户需求等。  
  编辑不改变流转类型与业务含义，仅修正或补充文字，保证链条完整、可追溯。

### 4.2 普通跟进（无 `transitionType`）

- **可删除**  
  仅管理员或该条跟进的创建者可删。
- **删除时一并删除其下所有图片**  
  - 先查该跟进下的所有 `crm_follow_up_image`，对每条调用 Vercel Blob 的 `del(blobUrl)` 删除文件。  
  - 再执行 `prisma.crm_follow_up.delete`；表结构上 `crm_follow_up_image` 对 `crm_follow_up` 为 `onDelete: Cascade`，因此 DB 中关联图片记录会随跟进删除而自动删除。  
  即：**普通记录删了之后，带的照片（Blob + DB）都会删掉**。

### 4.3 与四种方案的关系

- 最终策略**没有**采用 A/B/C/D 中「删除状态变更 + 按链顶/时间做撤回」的任何一种，而是**禁止删除状态变更记录**，用「只可编辑」来兼顾纠错与链条完整。
- 方案 A/B/C/D 仍保留为文档中的备选思路；若未来需要「允许撤销最后一步」的撤回能力，可在此基础上再设计独立的「撤回流转」操作（并生成新的「撤回」记录，而非删原记录）。

## 五、实现要点摘要

1. **Schema**  
   - `crm_follow_up` 有可选字段 `transitionType`（如 `lead_to_opportunity`、`opportunity_to_customer`），用于标识该条是否为「线索→商机」或「商机→客户」的状态变更。  
   - `crm_follow_up_image` 对 `crm_follow_up` 使用 `onDelete: Cascade`，保证删除跟进时 DB 侧图片记录被级联删除。

2. **删除逻辑（`deleteFollowUp` / `deleteFollowUpAction`）**  
   - 若该条存在 `transitionType`：不执行删除，直接返回错误。  
   - 否则：先按 `followUpId` 查出所有图片，逐个删除 Blob，再删除跟进（触发图片表级联删除）。

3. **编辑**  
   - `updateFollowUpAction`：仅管理员或该条创建者可编辑；可改字段包括 content、contactPerson、summary、nextStep、customerNeeds 等。  
   - 时间线三点菜单中，对所有有权限的跟进展示「编辑」；状态变更只展示「补充图片」+「编辑」，不展示「删除」。

4. **文档与后续**  
   - 四种方案及最终策略已整理入本文档（`docs/CRM_跟进记录删除与状态变更策略.md`），便于产品、开发与后续迭代参考。

---

## 六、总结表

| 项目 | 状态变更记录（带 transitionType） | 普通跟进 |
|------|-----------------------------------|----------|
| 是否可删 | 否（后端报错，前端不展示删除） | 是（创建者或管理员） |
| 删除时是否删图片 | 不适用 | 是（Blob + DB 级联） |
| 是否可编辑 | 是（描述与可选字段） | 是 |
| 链条与可追溯性 | 不删只改，链条完整 | 可删，按需清理 |

上述即为「四种方案 + 最终采用策略」的完整说明与实现要点。
